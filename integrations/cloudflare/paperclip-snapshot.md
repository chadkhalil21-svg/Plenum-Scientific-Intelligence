# Encrypted native snapshot candidate

Extends the existing GitHub/Cloudflare design without replacing Paperclip, its five divisions or eleven work products. This is an isolated storage core, NOT a deployed endpoint or production acceptance. Existing owner-only gates and public CI denial remain unchanged.

- The existing cold native backup script `integrations/prometheus_oss/native_restore.sh` proves same-job synthetic native volume recovery. It does not export raw native database bytes. The new module accepts opaque cold-backup bytes, encrypts with AES-256-GCM, binds company, mission, snapshot and exact source commit, and stores immutable 512 KiB ciphertext chunks with a commit manifest written last. It caps a single archive at 256 MiB. The key never enters the storage API. Every snapshot uses a fresh key under operator-controlled custody; retain its manifest digest independently. The caller must enforce this key lifecycle. Partial writes are permanently reserved, never automatically replayed or overwritten.
- The reserve/chunk/commit/read operations allow individual bounded requests; do not use the whole-bundle convenience wrapper inside the Worker for large snapshots. The storage contract targets the existing Cloudflare SQLite Durable Object storage API. A separately scoped owner-authorized transport candidate now exists in paperclip-snapshot-transport.mjs, using a distinct HMAC capability, exact company/mission/snapshot/commit scope, an explicit enable flag, preview denial, bounded bodies and a separate Durable Object binding. The candidate is registered in both equivalent Wrangler configurations but defaults to disabled, including previews. All scopes share a dedicated SQLite object with a conservative 256 MiB reservation budget (including per-snapshot overhead) and four snapshot reservations, including incomplete ones. No auto-delete or quota reset; owner-approved retention/rotation remains necessary. Account-wide headroom and Free-plan status still require independent verification. Private key custody, deployment authorization and actual live Cloudflare validation remain necessary. Do not reuse checkpoint HMAC keys, broaden existing checkpoint grants, deploy this module, or put production data/keys in the public GitHub repository or public CI. Existing checkpoint endpoints store only digests. The storage emulator test is not a Cloudflare deployment test.
- GitHub public standard runners may run the synthetic test only. To execute private production missions on GitHub requires a separately authorized trusted private execution policy, verified free allowance and zero-spend enforcement; the current owner gate explicitly rejects GitHub Actions. No authorization change is made here. No permanent server or paid model is required by the storage candidate.
- Next acceptance: on authorized runtime, validate the actual database archive and exact manifest, restore into an empty isolated native volume with no inference or external providers, independently read back original native company/mission and 5/11 outputs; separately qualify live Cloudflare scoped persistence and distinct-run recovery. Prove zero replay and paid_inference false. No claim of general autonomy, actual production recovery or live continuity from this component.

## Owner-only archive transport

The CLI `paperclip-snapshot-owner.mjs` refuses GitHub Actions and requires the confirmed private persistent runtime. It accepts exactly `upload PRIVATE_GRANT COLD_ARCHIVE ABSENT_RECEIPT` or `download PRIVATE_GRANT INDEPENDENT_RECEIPT ABSENT_ARCHIVE`. Inputs must be owner-owned mode-0600 regular files in owner-owned mode-0700 directories; output creation refuses existing destinations. The private grant contains only identity (company, mission, snapshot, source_commit), a fresh 32-byte AES key encoded as key_hex, and the separate snapshot HMAC secret. Never place these values in source, chat, command arguments or public CI. The client uses the exact existing Worker hostname, signed requests, bounded responses, no redirects, no automatic write retry and exact acknowledgment/hash checks. Owner must retain the independent receipt and key, ensure quiescence and a consistent cold database backup, verify real Free-plan headroom, and separately perform the native database restoration/readback. Downloading archive bytes is NOT restoring a native database. The CLI remains unexecuted in actual production.
