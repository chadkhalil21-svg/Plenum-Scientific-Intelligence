## Recommended communication experience
**Telegram group FIRST**: Create a private group for founder + Chief + Research + Coding. Hermes officially supports `@botusername` routing, allowlisted founder Telegram ID, `require_mention` and `exclusive_bot_mentions`; each separately named Telegram bot needs its **own BotFather token and separate Hermes profile**, though all named profiles can share a single configured multiplexing gateway process. A single generic bot can relay a roster menu, but individual Telegram names require distinct identities. Roll out 3 named profiles first, served by one configured multiplexing gateway where supported; add others only when useful. Do not run ten separate AI model loops.

On an approved free VM with an owner-supplied authenticated account (not in public GitHub):
1. Install official Hermes on that VM after reviewing source at the pinned commit above. Use the official installer docs, but do **not** pipe an unpinned remote shell script blindly.
2. Run `python integrations/hermes/provision_profiles.py` (shows plan without changing anything). Then `python integrations/hermes/provision_profiles.py --apply --roles chief research coding` in a trusted checkout. Existing profiles are left untouched.
3. Create **three distinct Telegram bots** through [@BotFather](https://t.me/BotFather); put their private tokens into **separate secured Hermes profile credential stores**, never into issues, .env.example, GitHub files or chat text. Obtain the founder's Telegram numeric user ID through the official Telegram app and set `TELEGRAM_ALLOWED_USERS` to **that one ID**, not `*`. Add each bot to the founder-owned private group.
4. Apply the official Telegram safety settings in each separate profile's private `config.yaml`:
   ```yaml
   telegram:
     require_mention: true
     exclusive_bot_mentions: true
     bots_require_mention: true
   ```
   Keep group sender allowlist narrow. Each role gets its own bot token, though profiles may share a gateway process. Do **not** set `TELEGRAM_ALLOW_BOTS=all` without explicit per-bot mention enforcement (loop risk). Use `hermes -p <role> gateway install` only after tokens, model, least-privilege toolsets and secure persistent host are configured and approved.
5. Add **the one status-reporting Telegram bot token** to the **private GitHub Actions secret** `PLENUM_TELEGRAM_BOT_TOKEN`, and private Telegram group ID to repository variable `PLENUM_TELEGRAM_CHAT_ID`. This opt-in receives verified-status summaries from currently supported public issue tasks; it does not allow members of Telegram to create private GitHub tasks. No secret or connection has been configured automatically.
6. Install the PUBLIC task bridge into the **Chief's own trusted Hermes profile only**, after the owner supplies a private least-privilege GitHub Issues token. The checked-in plugin at `integrations/hermes/plugins/plenum-public-workforce` is a source package, **not** a deployed/automatically discoverable Hermes plugin. Copy it only to that profile's private `plugins/plenum-public-workforce` directory, install Plenum's existing `plenum_ai` Python package into the same trusted Hermes Python environment, and explicitly enable `plenum-public-workforce` with `hermes -p chief plugins enable plenum-public-workforce`. Its owner token must be scoped to issues in the **public Plenum Scientific Intelligence repository only**, placed in the Chief profile's private `.env` as `PLENUM_GITHUB_PUBLIC_ISSUES_TOKEN` and never committed or copied into a group. The tool independently confirms token identity as the founder before a task is created, then the existing GitHub issue workflow handles the public task. This owner consent does not authorize private account operations. The tooling requires a small live provider test before claiming group-to-GitHub command works.
7. Coding role only, after plugin/security review: set `SUPERPOWERS_DISABLE_TELEMETRY=1` in its private runtime environment, then `hermes -p coding plugins install obra/superpowers --ref 22f0b463e7a5e579904dd6211a520321035526f7 --enable`. This is the upstream officially supported pinned plugin method. It should not enable file writes, shell, deployments or customer-account tools without separate granular approval.
7. **Prepared direct task bridge:** the new native Hermes plugin at `integrations/hermes/plugins/plenum-public-workforce/` exposes exactly two tools: `plenum_assign_public_task` (create an owner-authenticated PUBLIC Issue in the original Plenum queue) and `plenum_read_public_task_status` (read the recorded public work outcome only). The provider adapter is `src/plenum_ai/hermes_issue_bridge.py`, using exact GitHub owner identity, topic allowlists and strict provider readback. It performs no private app actions. On the **owner-controlled trusted Chief Hermes host** with the original Plenum Python package installed (`python -m pip install -e .`), copy this reviewed plugin directory into the **Chief profile's user plugin directory as documented by Hermes**, run `hermes -p chief plugins doctor /path/to/plenum-public-workforce --ci`, and only after review enable with `hermes -p chief plugins enable plenum-public-workforce`. Store an **owner-scoped, repository-limited GitHub Issues token** in the Chief profile's private environment variable `PLENUM_GITHUB_PUBLIC_ISSUES_TOKEN` (no broad admin/repos permissions), never in the other specialists' credentials. This token is distinct from and cannot be copied from ChatGPT's GitHub plugin.

   Then the intended end-to-end path is: founder `@chief_bot` message → Hermes Chief uses the approved `plenum_assign_public_task` tool → existing GitHub issue workflow sends it to an original Plenum specialist → GitHub bot posts verified public completion → Telegram group gets the opt-in status report. The source is ready, but the actual message path cannot be declared live until one real owner-authorized group task completes and is independently checked.

8. Talk to `@chief_bot`, `@research_bot`, or `@coding_bot` in a **private Telegram group**. Separate Hermes profiles have separate memories. The original Deep Agents Chief and nine n8n agents remain separately implemented; this adapter exposes ONLY the four existing PUBLIC Issue routes. There is **no automatic authorization** for private email, payments, cloud account management or customer records.

**WhatsApp**: Hermes can connect to WhatsApp group chats through the **unofficial Baileys bridge**, but the developer documents a risk of account restrictions and session credential exposure. Official Meta WhatsApp Cloud API currently supports only direct-message conversations in Hermes v1, and real groups are capability-gated. **Do not connect the founder's personal WhatsApp account to an unofficial always-on bridge.** Prefer Telegram group now and consider official WhatsApp Business direct messaging later if a dedicated business number and Meta permissions are authorized.
